01 · Conceptos esenciales

Primero, entiende las herramientas

Git registra la evolución del código; GitHub aloja repositorios remotos y facilita que un equipo revise, comparta y gestione cambios.

⑂

Git

Sistema de control de versiones distribuido. Guarda el historial de cambios mediante commits y permite trabajar con ramas.

●

GitHub

Plataforma para alojar repositorios remotos, invitar colaboradores, revisar pull requests, gestionar Issues y publicar sitios estáticos.

⌘

Git Bash + VS Code

Git Bash ofrece una terminal para ejecutar comandos. Visual Studio Code permite editar archivos e integrar las operaciones de Git.

02 · Ruta guiada

Del repositorio vacío al trabajo en equipo

Sigue los pasos en orden. Los comandos se pueden copiar y adaptar a tu proyecto.

1

Instala y configura Git

Instala Git, abre Git Bash o la terminal de VS Code y configura la identidad que aparecerá en tus commits.

git --version
git config --global user.name "Tu Nombre"
git config --global user.email "tu_correo@ejemplo.com"
git config --list
2

Crea el repositorio remoto

En GitHub, selecciona New repository, define nombre, descripción y visibilidad. Copia la URL HTTPS o SSH.

  • • Público: otras personas pueden ver el código.
  • • Privado: solo usuarios autorizados pueden acceder.
  • • Para este ejemplo, crea el repositorio sin README si vas a subir un proyecto local existente.
3

Inicializa y sube el proyecto

Ejemplo para una carpeta local nueva y un repositorio remoto vacío. Reemplaza la URL por la de tu repositorio.

mkdir mi-proyecto
cd mi-proyecto
git init
git add .
git commit -m "Primer commit"
git branch -M main
git remote add origin URL_DEL_REPOSITORIO
git push -u origin main

Nota: si la carpeta está vacía, crea primero un archivo, por ejemplo README.md. Si el repositorio remoto ya tiene commits, sincroniza el historial antes de intentar subirlo.

4

Clona el proyecto

Los colaboradores descargan una copia del repositorio para trabajar localmente.

git clone URL_DEL_REPOSITORIO
cd nombre-del-proyecto
git status

03 · Caja de herramientas

Comandos que usarás a diario

Consulta la descripción y copia los comandos según la tarea. Ejecuta los comandos desde la carpeta correcta del proyecto.

Revisar estado

Muestra archivos modificados, preparados o sin seguimiento.

git status

Preparar cambios

Agrega todos los cambios actuales al área de preparación.

git add .

Crear un commit

Guarda una instantánea con un mensaje descriptivo.

git commit -m "Describe el cambio"

Conectar remoto

Asocia el repositorio local con el remoto llamado origin.

git remote add origin URL_DEL_REPOSITORIO

Crear y cambiar

Crea una rama y te cambia a ella.

git switch -c feature/login

Listar ramas

Muestra las ramas locales.

git branch

Cambiar de rama

Cambia a una rama que ya existe.

git switch develop

Fusionar cambios

Integra la rama indicada en la rama actual.

git merge feature/login

Descargar e integrar

Trae cambios remotos e intenta integrarlos en la rama actual.

git pull origin develop

Publicar rama

Sube la rama y configura el seguimiento remoto.

git push -u origin feature/login

Consultar remotos

Muestra las URL de los remotos configurados.

git remote -v

Traer referencias

Actualiza referencias remotas sin integrar los cambios automáticamente.

git fetch origin

Historial compacto

Muestra commits resumidos en una línea.

git log --oneline

Ver diferencias

Muestra cambios que aún no están preparados.

git diff

04 · Flujo de ramas

Organiza el trabajo con main, develop y feature

Este flujo mantiene separadas las versiones estables de la integración y del trabajo individual. Es una estrategia recomendada, no una obligación para todos los proyectos.

main

Rama estable. Contiene versiones validadas y listas para entregar o publicar.

develop

Rama de integración donde se reúnen funcionalidades antes de preparar una versión estable.

feature/*

Ramas temporales para desarrollar una funcionalidad sin trabajar directamente en main.

A. Crear y publicar develop

Ejecuta estos comandos después de clonar el repositorio y verificar que main está sincronizada.

git switch main
git pull origin main
git switch -c develop
git push -u origin develop

B. Crear una funcionalidad

Cada colaborador crea su rama desde develop, trabaja, registra sus cambios y la publica.

git switch develop
git pull origin develop
git switch -c feature/nueva-funcionalidad
git add .
git commit -m "Agrega funcionalidad"
git push -u origin feature/nueva-funcionalidad

Módulo de reportes

Cada persona abre un pull request hacia develop. El líder revisa y aprueba. Cuando el equipo valida el conjunto de cambios, se crea un pull request de develop hacia main.

05 · Trabajo en equipo

Comparte el repositorio con colaboradores

El líder del proyecto puede conceder acceso directo al repositorio. En repositorios de una organización, las opciones pueden variar según los permisos configurados.

  1. 1

    Abre la configuración

    En el repositorio, entra en Settings y busca Collaborators o la sección de acceso correspondiente.

  2. 2

    Invita al equipo

    Busca el usuario de GitHub, envía la invitación y confirma que cada persona la acepte.

  3. 3

    Define las responsabilidades

    Asigna funcionalidades e Issues. Acuerden nombres de ramas, mensajes de commit, revisores y reglas de integración.

  4. 4

    Sincroniza antes de trabajar

    Actualiza la rama base antes de crear una rama nueva. Evita trabajar directamente sobre main si el equipo utiliza revisión por pull request.

¿Colaborador directo o contribuyente externo?

Un colaborador directo recibe permisos en el repositorio original. Un contribuyente externo puede trabajar desde un fork y proponer cambios mediante un pull request, sin recibir acceso de escritura al repositorio original.

06 · Revisión de código

Pull Requests: revisar antes de integrar

Un pull request propone integrar los cambios de una rama en otra. Permite conversar, revisar diferencias, ejecutar comprobaciones y resolver observaciones antes de fusionar.

⑂

1. Publica la rama

Usa git push para subir tus commits a GitHub.

⌕

2. Compara ramas

Selecciona la rama de origen y el destino: por ejemplo, feature → develop.

✓

3. Revisa y ajusta

El equipo comenta, solicita cambios y comprueba que el código funcione.

⇄

4. Integra cambios

Una persona autorizada fusiona el pull request cuando cumple las reglas del proyecto.

Buenas prácticas de pull request

  • ✓ Usa un título concreto y una descripción clara.
  • ✓ Mantén los cambios enfocados en una tarea.
  • ✓ Vincula el Issue relacionado cuando exista.
  • ✓ Resuelve conflictos y revisa los archivos modificados.
  • ✓ Solicita revisión antes de integrar.
  • ✓ Elimina la rama temporal si ya no se necesita.

GitHub ofrece opciones como Create a merge commit, Squash and merge y Rebase and merge. El equipo debe acordar la estrategia según su flujo de trabajo.

07 · Organización

Gestiona tareas con Issues

Los Issues permiten registrar errores, proponer funcionalidades, asignar responsables y documentar el avance. Con etiquetas e hitos, el equipo puede priorizar el trabajo.

¿Qué debe incluir un Issue?

  • • Título concreto
  • • Contexto y descripción
  • • Pasos para reproducir un error, si aplica
  • • Resultado esperado y resultado obtenido
  • • Responsable, etiquetas y fecha o hito si corresponde

08 · Publicación

Publica tu landing con GitHub Pages

GitHub Pages permite servir sitios estáticos desde un repositorio. Es adecuado para HTML, CSS y JavaScript del lado del cliente.

Pasos para publicar

  1. 01. Sube el archivo index.html y los recursos al repositorio.
  2. 02. Abre Settings → Pages.
  3. 03. En Build and deployment, selecciona la fuente disponible, normalmente Deploy from a branch.
  4. 04. Selecciona la rama y carpeta de publicación, por ejemplo main y /(root).
  5. 05. Guarda y espera a que finalice el despliegue; visita la URL mostrada en Pages.
🚀

Importante: frontend vs. backend

GitHub Pages publica contenido estático; no ejecuta un servidor FastAPI, Node.js ni una base de datos. Si tu proyecto necesita un backend, debes desplegarlo en un servicio compatible y configurar la URL de la API en el frontend.

Después de actualizar el sitio, registra los cambios con Git y súbelos a la rama configurada para que se publique una nueva versión.

09 · Solución de problemas

Errores frecuentes y cómo abordarlos

Abre cada pregunta para consultar una orientación inicial. Antes de ejecutar comandos que sobrescriban archivos o historial, revisa el estado y conserva una copia de los cambios importantes.

Comprueba el remoto con git remote -v. Si la URL es correcta, no necesitas volver a agregarlo. Si es incorrecta, puedes actualizarla con git remote set-url origin URL_DEL_REPOSITORIO.
Revisa la conexión, la autenticación, la URL remota, la rama actual y los permisos. Si el remoto tiene commits que no existen localmente, primero trae e integra los cambios de forma segura. GitHub no acepta la contraseña normal de la cuenta para autenticación Git por HTTPS; usa un método admitido, como Git Credential Manager o SSH.
Ejecuta git status, abre los archivos en conflicto, decide qué contenido conservar y elimina los marcadores de conflicto. Después ejecuta git add ARCHIVO y completa la operación con el commit o la acción que Git solicite. Si no sabes cómo continuar, consulta el estado antes de abortar la operación.
git fetch actualiza referencias remotas sin integrar los cambios; git pull obtiene cambios e intenta integrarlos en la rama actual; git push publica commits locales en el repositorio remoto.
No subas contraseñas, tokens, claves privadas ni archivos con datos sensibles. Usa variables de entorno locales, añade los archivos correspondientes a .gitignore antes de registrarlos y rota cualquier secreto que se haya expuesto. Añadirlo a .gitignore no elimina un secreto que ya está en el historial.
